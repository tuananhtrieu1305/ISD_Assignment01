1 What Is a Multiagent System?
An intelligent agentis a computational entity that perceives its environment and selects actions to
achieve objectives. Amultiagent system(MAS) consists of multiple agents whose actions interact
through messages, shared state, or a common environment.
Examples include shopping assistants, autonomous vehicles, traffic-control systems, robotic teams,
and distributed scheduling applications.
1.1 From an AI model to an intelligent system
A machine-learning model may predict a class or estimate a score. An intelligent application must
additionally manage data, state, decisions, external services, errors, and user interaction.
A practical system may contain:
• a user-interface component;
• a coordinator or workflow manager;
• specialized agents;
• databases and external services;
• validation and access-control rules;
• monitoring and evaluation components.
1.2 Main elements
Agent: A component with a role and decision policy.
Environment: The world or application state in which the agents operate.
Percept: Information available to an agent.
Action: An operation that changes state or produces an outcome.
Goal: A desired condition or performance objective.
Message: Information exchanged between agents.
Coordination: Mechanisms for ordering or reconciling agent actions.
1.3 Example
A shopping assistant may use a catalog agent to retrieve products, a recommendation agent to rank
them, and an inventory agent to verify availability. A coordinator combines the results into a response.
A collection of functions is not automatically a MAS. Agent boundaries should represent meaningful
responsibilities, decision policies, or independently evolving services.

2.2 Centralized coordination
A central coordinator receives a request, assigns tasks, collects outputs, and decides what to do next.
Advantages:
• straightforward workflow control;
• easier debugging and monitoring;
• explicit validation of final outputs.
Limitations include a possible bottleneck and dependence on the coordinator.
2.3 Distributed coordination
Agents make local decisions and coordinate through messages, events, negotiation, or shared state.
This can improve autonomy and scalability but introduces challenges involving conflicts, consistency,
and failures.
2.4 When is MAS useful?
A multiagent approach is particularly useful when a problem naturally decomposes into different
responsibilities, when components use different tools or policies, or when coordination between decisions
has measurable value.
Design principle: Do not introduce agents merely to increase the number of components. Every
agent introduces communication, testing, and maintenance costs.

3 Concepts for Understanding Intelligent Agents
3.1 Agent perception and action
At timet, an agent receives a perceptot, maintains internal statebt if required, and chooses an action
at.
A simple policy can be represented by
at =π(ot).
A stateful policy may be represented as
at =π(bt,o t),
where the internal state summarizes relevant past observations.
A stochastic policy can be written as
π(a|o) = P (at =a|ot =o).
3.2 PEAS task specification
PEAS stands for Performance measure, Environment, Actuators, and Sensors. It provides a structured
way to describe an agent’s task.
Example: tourism itinerary agent
• Performance: preference match, budget compliance, feasible travel time.
• Environment: attractions, transport, opening hours, user constraints.
• Actuators: propose, add, remove, or reorder stops.
• Sensors: preferences, map results, schedules, weather.
3.3 Rationality
A rational agent selects an action expected to perform well according to its objective, given its available
information, knowledge, and computational resources.
Rationality does not imply perfect knowledge. Data may be incomplete, noisy, or outdated.
3.4 Important properties
• Autonomy: decisions are based on the agent’s policy and state.
• Reactivity: the agent responds to changes.
• Proactiveness: the agent plans toward goals.
• Social ability: the agent communicates.
• Learning: the agent improves from data or feedback.

4 Environments, Goals, and Agent Architectures
4.1 Environment characteristics
An environment can be described along several dimensions:
• fully or partially observable;
• deterministic or stochastic;
• episodic or sequential;
• static or dynamic;
• discrete or continuous;
• single-agent or multiagent.
These distinctions affect how an agent should represent uncertainty, plan, and react to events.
4.2 Common architectures
Reactive agentsuse condition–action rules. They are often fast and interpretable.
Deliberative agentsmaintain a representation of states, goals, and possible plans.
Belief–Desire–Intention (BDI) agentsdistinguish beliefs about the world, desired outcomes,
and committed plans.
Utility-based agentscompare candidate actions using a utility function:
a∗ = arg max
a∈A
U (a).
Learning agentsuse data to estimate predictions or improve decision policies.
Hybrid agentscombine rules, planning, retrieval, learned models, and tools.
4.3 Recommended student architecture
For an introductory MAS project, a hybrid architecture is usually practical:
1. rules enforce hard constraints and safety;
2. retrieval obtains current facts;
3. a learned model classifies or ranks candidates;
4. a coordinator controls the workflow;
5. a human reviews consequential decisions.
A language model can be included as a component, but natural-language generation alone does not
provide reliable state management, authorization, or coordination.

5.3 Communication patterns
• Request–response: one agent asks another for a result.
• Publish–subscribe: agents receive relevant events.
• Shared workspace: agents use controlled shared state.
• Negotiation: agents propose alternatives and resolve conflicts under explicit rules.
5.4 Coordination invariants
Examples of invariants that must remain true:
• A booking is not confirmed until the booking service confirms it.
• A recommendation must not imply verified stock when inventory has not been checked.
• A healthcare support model must not present an unverified prediction as a diagnosis.

6 Engineering Workflow: From Problem to MAS
A disciplined engineering workflow reduces complexity and makes the system testable.
1. Define the user problem and measurable success criteria.
2. Identify environment entities, data sources, and tools.
3. Decompose the task into coherent agent responsibilities.
4. Define message schemas and access permissions.
5. Specify ordering, timeouts, retries, and fallback policies.
6. Implement a minimal end-to-end working example.
7. Test normal inputs, edge cases, and failures.
8. Compare performance against a suitable baseline.
9. Deploy behind an interface and monitor outcomes.
10. Revise the system using evidence and feedback.
6.1 Agent specification template
For each agent, document:
• name and responsibility;
• input and output schemas;
• permitted tools and data;
• decision policy;
• expected failure modes;
• success metric and tests.
6.2 Why explicit contracts matter
An agent’s output should be validated before it is consumed by another agent. For example, a recom-
mendation agent should return a list of known product identifiers, not arbitrary product descriptions.
The coordinator should enforce workflow rules rather than blindly trusting the outputs of internal
components.
6.3 Minimum viable implementation
Begin with two agents and one coordinator. Add more agents only when their responsibilities are
distinct and their contribution can be evaluated.

11 Coordination, Failure Handling, and Monitoring
A coordinator is a workflow controller. It decides which agent to call, validates outputs, and handles
missing or inconsistent information.
11.1 Failure scenarios
Typical failures include:
• an agent times out;
• a message has an invalid payload;
• a database returns no records;
• a service returns stale information;
• two agents produce incompatible results.

11.3 Metrics
Task completion rate:Fraction of requests that meet the task definition.
Latency: Median and 95th-percentile response time.
Coordination overhead: Messages and model/tool calls per request.
Quality: Relevance and constraint satisfaction.
Reliability: Failures, timeouts, and recovery success.
Safety: Unauthorized actions and unsupported claims.
11.4 Reproducibility
Record model and policy versions, message sequence, timestamps, and final outcomes. Avoid logging
secrets or unnecessary personal data. A fixed random seed improves experimental repeatability but
does not establish real-world validity.

12 Case Study A: E-commerce Shopping Assistant
12.1 Problem definition
A customer requests products that satisfy preferences, budget, and other constraints. The system
should retrieve real candidates, rank them, verify relevant details, and explain the recommendations.
12.2 Agent roles
• Intent agent:classifies the request.
• Catalog agent:retrieves products.
• Recommendation agent:ranks candidates.
• Inventory agent:verifies stock.
• Policy agent:checks business constraints.
• Coordinator: manages the workflow.
12.3 Workflow
Customer request→ intent classification→ catalog retrieval→ constraint filtering→
ranking→ inventory verification→ response
12.4 Evaluation
Possible metrics include:
• Recall@k for retrieval;
• NDCG@k for ranking quality;
• budget-violation rate;
• unsupported-availability claims;
• task completion and latency.
Compare the MAS with a single-agent baseline using the same requests, catalog, and evaluation
criteria.
12.5 Ethical considerations
Avoid manipulative ranking and undisclosed sponsored placement. Clearly distinguish relevance-
based ranking from paid promotion. Do not place orders or charge payments without explicit user
confirmation.

13 Case Study B: Tourism and Itinerary Planning
13.1 Problem definition
A traveler wants an itinerary based on dates, interests, budget, travel time, opening hours, and personal
constraints. The itinerary must be both useful and feasible.
13.2 Agent roles
• Preference agent: collects interests and constraints.
• Attraction agent: retrieves candidate destinations.
• Route agent: estimates travel times and ordering.
• Budget agent: estimates costs.
• Context agent: retrieves relevant weather or event data.
• Coordinator: reconciles conflicts and produces the plan.

14 Case Study C: Healthcare Support
14.1 Scope and safety boundary
A student prototype should focus on administrative or educational support rather than autonomous
diagnosis or treatment. Examples include appointment preparation, clinic navigation, and organizing
questions for a clinician.
14.2 Agent roles
• Intake agent:clarifies the administrative need.
• Information agent:retrieves approved educational material.
• Scheduling agent:queries appointment slots.
• Preparation agent:creates a neutral checklist.
• Safety agent:identifies cases requiring professional or emergency support.
• Coordinator: enforces permissions and workflow.
14.3 Example workflow
A user requests help preparing for a clinic visit.
1. The intake agent clarifies the purpose and logistics.
2. The information agent retrieves approved clinic material.
3. The preparation agent generates a checklist.
4. The user reviews the checklist.
5. Qualified healthcare personnel remain responsible for clinical decisions.
14.4 Safety requirements
• Minimize personal-data collection.
• Use consent, access controls, and secure storage.
• Label generated content and identify its source.
• Never fabricate appointments, test results, or records.
• Escalate urgent or high-risk requests appropriately.
• Require confirmation before booking or changing records.
14.5 Evaluation
Measure information correctness, task completion, privacy compliance, escalation sensitivity, false
reassurance, and usability. The system must not present an unverified model output as a professional
medical judgment.

Despite different application requirements, all three systems benefit from:
• explicit agent responsibilities;
• structured communication;
• verification of important facts;

16 Experimental Design and Evaluation
A working demonstration is necessary but insufficient. A student project should test whether the MAS
improves a measurable property relative to a suitable baseline.
16.1 Baselines
B0: Single-agent pipeline.
B1: Rule-based multiagent system.
B2: Multiagent system with a learned component.
B3: Ablation without coordinator validation.
16.2 Experimental controls
All systems should use the same test requests, data sources, and task definitions. A held-out test set
should be kept separate from training and model selection.
16.3 Suggested metrics
• task completion rate;
• domain-specific relevance or accuracy;
• constraint satisfaction rate;
• median and 95th-percentile latency;
• messages and tool calls per request;
• failure recovery rate;
• safety violations.

18.2 Common mistakes
• Calling several ordinary functions “agents” without meaningful independent responsibilities.
• Using an untrained neural network and treating its predictions as valid.
• Allowing agents to invent facts absent from the data.
• Ignoring timeouts, duplicate actions, or malformed data.
• Evaluating only accuracy while ignoring safety and latency.
• Using personal data without appropriate justification and safeguards.
• Reporting improvements without a fair baseline.

19.1 Final design checklist
Before presenting a multiagent system, verify that:
1. the problem and success criteria are explicit;
2. each agent has a coherent responsibility;
3. inputs and outputs follow defined schemas;
4. permissions and access to data are controlled;
5. the coordinator validates results;
6. external facts are verified when freshness matters;
7. learned components are trained and evaluated;
8. tests cover normal, boundary, and failure cases;
9. logs support debugging without unnecessary personal data;
10. consequential actions require suitable confirmation.

19.3 Conclusion
A multiagent system is an engineered collaboration among decision-making components. Strong
implementations combine clear roles, structured communication, grounded information, measurable
evaluation, safe failure handling, and human-centered workflows.
The goal is not to maximize the number of agents. It is to design a system in which coordination
produces measurable benefits over a simpler alternative.
